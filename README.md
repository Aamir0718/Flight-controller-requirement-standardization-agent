# Flight Controller Requirements Agent

Offline requirements-engineering agent for flight controller requirement
spreadsheets. Parses messy Excel requirement sheets, rewrites each
requirement into EARS-compliant candidates, scores them against the INCOSE
rulebook in plain Python, and recommends the best candidate — with a local
Ollama model doing the rewriting and nothing else.

> Status: ingestion parsing, golden-data prep, rules (detectors, EARS
> classifier, INCOSE scorer/rulebook, rule selector), llm (local Ollama
> client, prompt assembly), pipeline (candidate generation, recommender,
> LangGraph orchestration), storage (SQLite + Excel export), and ui
> (FastAPI backend + Streamlit frontend) are all implemented.

## Layout

```
src/
  ingestion/   Excel parsing (src/ingestion/parser.py)
  data_prep/   consolidates data/reference/ into data/golden/ few-shot
               and eval splits (src/data_prep/consolidate.py)
  rules/       regex/keyword defect detectors, EARS classifier,
               INCOSE rulebook loader and scorer
  llm/         local LLM (Ollama) wrapper and prompt templates
  pipeline/    LangGraph orchestration
  storage/     SQLite traceability layer + Excel export (src/storage/db.py)
  ui/          FastAPI backend (api.py: upload / run status / download,
               loopback only) + Streamlit frontend (streamlit_app.py:
               upload button, progress, results table, download button)
  config.py    loads config/settings.yaml
data/
  reference/   EARS/INCOSE reference material and labeled examples
  golden/      few-shot.json (150 rows) / eval.json (60 rows, held out
               until Week 4 evaluation) — generated by data_prep.consolidate
config/
  settings.yaml  Ollama model name, host/port, and other tunables
tests/
  fixtures/    synthetic messy .xlsx files for parser tests
scripts/
  setup_env.ps1, run_tests.ps1, run_api.ps1, run_streamlit.ps1
  evaluate.py           scores the full pipeline against the 60 held-out
                         data/golden/eval.json examples -> data/eval_results.json
  robustness_check.py   runs 15-20 hand-written (not golden-set) requirements,
                         incl. malformed/edge-case input -> data/robustness_results.json
  verify_offline.py     runs the full pipeline under a network guard that
                         blocks any non-loopback connection attempt --
                         required pre-release, see "Pre-release checklist" below
```

## Setup

```powershell
scripts\setup_env.ps1
```

This creates `.venv`, installs pinned dependencies from `requirements.txt`,
and installs the `src` packages in editable mode.

## Running

```powershell
scripts\run_tests.ps1
scripts\run_api.ps1         # FastAPI backend
scripts\run_streamlit.ps1   # Streamlit UI
```

## Configuration

All tunables (Ollama model name, host/port, storage paths, pipeline
settings) live in `config/settings.yaml` — never hardcode them in
application code. Load them via `config.get_settings()`.

## Requirements

- Fully offline at runtime: the only network call is to a locally-running
  Ollama instance.
- Storage is a single local SQLite file.
- Must run unmodified on air-gapped machines after setup.

## Pre-release checklist

Every release must pass all of the following, in order, before shipping:

1. **Full test suite green.**
   ```powershell
   scripts\run_tests.ps1
   ```

2. **Evaluation run against the held-out golden set.** Requires Ollama
   running locally (`ollama serve` + the model configured in
   `config/settings.yaml` pulled). Review `data/eval_results.json` for
   regressions before release — in particular the EARS-classification
   accuracy, the invented-number rate (must be 0%), and the failure list.
   ```powershell
   .venv\Scripts\python.exe scripts\evaluate.py
   ```

3. **Robustness check.** Same Ollama requirement. Confirms nothing
   crashes and nothing silently fails on malformed/edge-case input.
   `data/robustness_results.json`'s `all_cases_handled_safely` must be
   `true`.
   ```powershell
   .venv\Scripts\python.exe scripts\robustness_check.py
   ```

4. **Automated offline check.**
   ```powershell
   .venv\Scripts\python.exe scripts\verify_offline.py
   ```
   This must print `PASS`. It is a fast, useful, CI-friendly smoke check
   — but it is an **in-process** guard (it monkeypatches Python's socket
   layer) and cannot see network activity from C extensions, subprocesses,
   or anything outside this process. **It is necessary, not sufficient.**

5. **Physical offline test — REQUIRED, not optional.** The only test
   that actually verifies the "runs on an air-gapped machine" claim in
   the Requirements section above is running this software on a machine
   with its network physically disconnected:
   - Unplug the Ethernet cable **and** disable Wi-Fi **and** disable any
     mobile/cellular radio (airplane mode is not enough by itself if
     Wi-Fi/Bluetooth stay on — turn each radio off explicitly).
   - With Ollama already running locally and a model already pulled
     (pulling a model *is* a network call — do this before disconnecting),
     run `scripts\verify_offline.py` and then a full manual pass through
     the UI/pipeline on a real sample sheet.
   - Confirm nothing hangs, errors, or silently degrades with the network
     gone. Any behavioral difference between the connected and
     physically-disconnected runs is a release blocker.
   - Do this on the actual target hardware/OS image when possible, since
     OS-level network services (updaters, telemetry, etc.) vary by
     machine and aren't something step 4 can see at all.

Steps 2-4 can be scripted into CI. Step 5 cannot — it requires a person
with physical access to the machine, and must be repeated for every
release, not just the first one.
